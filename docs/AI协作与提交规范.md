# AI 研发协作规范

> 本规范适用于 Android、PDA、前端、服务端及其他研发任务。
> 目标不是限制 AI 写代码，而是让 AI **先理解、再开发、能自检、可复审、最终可交付**。

## 一、基本原则

1. **先理解，再执行**
   - 开始开发前先阅读项目已有的 `CLAUDE.md`、`README.md`、编码规范及相关需求文档。
   - 优先理解现有工程结构、技术栈、业务逻辑和已有实现，不要拿到需求立即写代码。
2. **规范优先级**
   - 当前用户明确指令 > 项目已有规范 > 本通用规范。
   - 如果不同资料之间存在冲突，必须先指出冲突，不得自行猜测口径。
3. **AI 必须有判断**
   - 不要机械执行明显不合理、有风险或存在设计问题的指令。
   - 发现更合理的实现方式、潜在风险或需求矛盾时，应主动说明原因并给出建议。
   - 缺少会影响结论的关键需求、接口、代码或上下文时，应先提出，不得靠猜测补齐事实。
4. **控制修改范围**
   - 只修改当前任务直接相关内容。
   - 不顺手重构、不顺手升级依赖、不顺手修改无关代码、不顺手修历史 Bug。
   - 发现无关问题可以记录并汇报，未经明确要求不要扩大任务范围。
5. **避免过度设计**
   - 优先采用简单、直接、符合现有工程风格的方案。
   - 不为尚未出现的未来需求提前设计大量接口、Manager、Factory、Strategy 等抽象。
   - 确实需要新增模块、分层或抽象时，应能够说明其必要性。

------

## 二、代码实现要求

1. **遵循现有工程**
   - 优先复用已有基础类、工具类、Toast、Dialog、Loading、日志、网络、缓存等公共能力。
   - 不重复造轮子。
   - 新代码的目录、命名、调用方式和代码风格尽量与原工程一致。
2. **命名必须准确**
   - 类、方法、变量、常量、枚举、接口等名称应准确表达真实业务含义。
   - 禁止复制旧代码后留下错误或误导性的命名。
3. **关键逻辑必须有中文注释**
   - 业务规则、兼容逻辑、特殊边界、临时方案、非显而易见的处理必须说明“为什么这样做”。
   - 枚举、重要常量、公共接口及容易产生误解的字段应有必要注释。
   - 不为简单赋值和显而易见的代码增加无意义注释。
4. **及时删除冗余代码**
   - 清理废弃逻辑、未使用变量、无用 import、临时 Mock、调试代码和已经被新逻辑替代的旧实现。
   - 不允许为了“保险”长期保留两套实际只需要一套的逻辑。
5. **用户可见文案必须资源化**
   - 页面、Toast、Dialog、按钮、标题、错误提示、Loading、空状态等用户能够看到的文字，不应直接硬编码在业务代码中。
   - Android 使用 `strings.xml` 或工程已有资源体系；其他项目遵循自身国际化/资源体系。
   - 不要求顺手清理与当前任务无关的历史硬编码。

------

## 三、健壮性与界面要求

1. **空值和集合必须安全**
   - 注意 `null`、空字符串、空对象、空数组、空列表以及数组越界。
   - 不直接假设接口字段、集合第一项或异步结果一定存在。
2. **异常必须有合理处理**
   - 网络失败、解析失败、权限问题、设备异常、接口异常等不能静默失败。
   - 用户需要知道的异常应提供合理提示，同时保留足够的定位日志。
3. **注意并发和重复操作**
   - 防止重复点击、重复提交、重复请求、并发上传以及异步回调乱序。
   - 涉及批量数据时应关注分页、分批、去重、限流以及实际业务数据量。
4. **注意生命周期**
   - Activity、Fragment、页面销毁后，不应继续更新失效 UI。
   - 定时器、监听器、广播、协程、异步任务等应按项目技术栈正确释放。
5. **界面不能“炸”**
   - 文本过长、字段为空、不同屏幕尺寸等情况下都应保持基本可用。
   - 可根据需要采用换行、字体适配、宽高自适应、滚动等方式。
   - 不为了固定高度或固定宽度导致内容截断、重叠或页面布局异常。
6. **保持现有视觉风格**
   - 优先复用现有颜色、间距、按钮、弹窗、Loading、空状态等视觉规范。
   - 不为一个局部功能重新设计一套与工程明显不同的 UI。

------

## 四、日志与敏感信息

1. **关键节点必须有必要日志**
   - 重要流程开始/结束、接口异常、状态变化、设备或 SDK 异常等应保留能够定位问题的信息。
   - 高频循环和高频读取场景应避免无限打印日志。
2. **Debug / 测试环境**
   - 可以保留充分的工程定位信息和业务样例，优先保证问题能够被定位。
3. **生产环境 / 对外材料**
   - 密码、Token、密钥、真实生产凭证等禁止输出或提交。
   - 客户隐私、账号、生产业务数据等按需要脱敏。
   - 对外截图、公开文档和公开仓库必须额外检查敏感信息。
4. **凭证类信息任何环境都应谨慎处理**
   - 不因为 Debug 环境就把密码、Token、密钥等长期写入代码或提交 Git。

------

## 五、开发完成后的自检

代码完成后，在汇报之前至少检查：

- 是否只修改了本任务相关文件。
- 是否存在明显冗余代码或临时调试代码。
- 用户可见文案是否正确资源化。
- 关键逻辑是否有必要中文注释。
- null、空集合、数组越界及异常场景是否处理。
- 是否存在重复点击、并发或生命周期风险。
- 页面在长文本、空数据等情况下是否能够正常展示。
- 是否复用了工程已有能力和样式。
- 是否引入了不必要的抽象或新依赖。
- 日志是否足够定位问题，同时避免敏感信息泄露。
- `git diff` 和 `git status` 是否符合预期。
- 是否完成当前条件允许的最小构建、编译、单测或其他验证。

无法执行某项验证时，不得假装已经验证，应在汇报中明确说明。

------

## 六、Git 规则

1. 完成开发和自检后，默认可以使用**简短中文 commit** 提交本轮相关修改。
2. commit 前必须检查 `git status` 和 `git diff`，不得把无关修改一起提交。
3. commit 信息应简洁准确，例如：
   - `新增NFC内容解析模块`
   - `修正盘点上传异常处理`
   - `优化设备兼容逻辑`
4. **默认禁止 push。**
5. 只有用户明确要求或当前任务已经明确授权 push 时，才允许执行 `git push`。
6. 如果当前任务明确要求“不 commit”，则不得提交。

------

## 七、完成后的汇报

每轮任务结束必须有简洁汇报，至少包含：

1. **完成内容**：本轮做了什么。
2. **主要修改**：涉及哪些核心文件或模块，以及关键变化。
3. **验证结果**：执行了哪些构建、测试或检查，结果如何。
4. **风险与待确认项**：仍存在什么问题、限制或需要用户确认的事项。
5. **Git 状态**：是否 commit、commit 信息或 hash、是否 push。

如果本轮同时生成或更新了文档，还应补充：

- 文档主要记录了什么；
- 文档保存位置；
- 是否还有待补充内容。

------

## 八、最终原则

AI 的目标不是“按照指令把代码写出来”，而是：

**理解需求 → 判断方案 → 遵循工程 → 完成开发 → 主动自检 → 接受复审 → 验证结果 → 清晰交付。**

遇到不合理之处要指出，遇到不确定事实要确认，遇到风险要说明。

任务执行过程中，如果确实有更好的方案，你可以使用更好的方案处理，但汇报时，需要说明原因。

**不要机械执行，不要过度设计，不要留下无法解释和无法验证的代码，总之，你需要有自己的思维和判断，不是呆板的执行机器。**
